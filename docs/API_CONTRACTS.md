## 1. Purpose and boundary

This document specifies the **internal application API** used by the CAI frontend and backend.

It does not define:
- Gemini's vendor-specific API request format;
- Supabase's internal service APIs;
- automatic college website ingestion;
- ERP integrations.

MVP behavior:
- notices are uploaded manually by authorized uploaders;
- public visitors can browse published notices without login;
- uploader actions require authentication and backend authorization;
- passing notices may publish automatically after validation;
- held notices require review;
- search and Ask use published notice content only;
- the original notice remains authoritative.

## 2. API principles

1. The frontend communicates with the FastAPI backend for application data and actions.
2. The browser never receives the Supabase service-role key or Gemini API key.
3. Public endpoints return published, public-safe records only.
4. Protected endpoints verify identity and application permission on the backend.
5. Accepted upload is not the same as published notice.
6. All list responses use predictable pagination.
7. Dates and page references are preserved.
8. AI answers must be grounded in retrieved published notice evidence.
9. Errors use a consistent machine-readable format.
10. Contract changes require coordination with affected module owners.

## 3. Conventions

### 3.1 Base path

All routes are under:

`/api/v1`

Example: `GET /api/v1/notices`

### 3.2 Content types

- JSON: `application/json`
- File upload: `multipart/form-data`
- JSON responses: `application/json`

### 3.3 IDs

IDs are opaque strings generated by the backend, normally UUIDs for notice resources. The frontend must not construct IDs or assume sequential values.

### 3.4 Date and time formats

- Date-only values: `YYYY-MM-DD`.
- Timestamps: ISO 8601 with timezone offset or `Z`.
- Time-only values: `HH:MM:SS` or a documented shorter ISO-compatible time form.
- Do not invent a time when a source gives only a date.
- Keep issue date, event date, and deadline distinct.

### 3.5 Pagination

List routes accept:
- `limit` — requested page size; backend applies a maximum.
- `offset` — number of records to skip.

Response:

```json
{
  "items": [],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 0,
    "has_more": false
  }
}
```

The backend may choose a default limit. The maximum must be configured and documented before deployment.

### 3.6 Common error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request could not be processed.",
    "details": [
      {
        "field": "file",
        "issue": "Unsupported file type."
      }
    ],
    "request_id": "request-id"
  }
}
```

- `code` is stable and machine-readable.
- `message` is safe for display.
- `details` is optional.
- `request_id` is recommended.
- Never return stack traces, credentials, environment variables, or raw provider secrets.

> [!IMPORTANT]
> **FastAPI Error Handling Requirement:** FastAPI defaults to returning `{"detail": [...]}` for validation errors (422) and standard HTTP exceptions. The backend application must configure custom exception handlers for `RequestValidationError` and `StarletteHTTPException` to transform all error responses into this `{ "error": { "code", "message", "details", "request_id" } }` envelope.

## 4. Authentication and authorization

### Public routes

No user login is required. Public routes expose published and public-safe information only.

### Uploader routes

Uploader routes require a valid Supabase Auth access token:

`Authorization: Bearer <access-token>`

The backend must:
1. verify the token;
2. resolve the user's application role;
3. check permission for the requested action;
4. reject missing/invalid identity with `401`;
5. reject an authenticated but unauthorized user with `403`.

Application roles:
- `uploader`
- `admin`

A signed-in user who has no `profiles` record has no application role and is rejected with `403`. Authentication alone never grants uploader permission.

Uploader routes are available to the `uploader` and `admin` roles unless the final role-to-action matrix (an open decision, see §13) states otherwise. The database stores only the role value; the matrix is enforced by the backend. The frontend must not be trusted to supply its own role.

## 5. Shared response shapes

These are API shapes, not direct database table dumps. Internal fields such as `storage_path`, raw model output, service metadata, and private processing logs must never be returned to public clients.

### 5.1 Audience values and the audience filter

Audience values:

```json
[
  {"id": "student", "label": "Students"},
  {"id": "faculty", "label": "Faculty"},
  {"id": "staff", "label": "Staff"},
  {"id": "all", "label": "Everyone"},
  {"id": "unspecified", "label": "Not specified"}
]
```

`unspecified` is not equivalent to `all`.

The optional `audience` query parameter used by `/briefing`, `/notices`, `/search`, and `/ask` behaves as follows:

- Omitted, or `all`: the unfiltered view. Every eligible published notice is included, and notices whose audience is `unspecified` are included and labelled "Not specified". Here `all` means "no audience filter"; it is distinct from the `all` target value a notice can carry.
- `student`, `faculty`, or `staff`: notices targeted to that role, plus notices targeted to `all`.
- `unspecified`: only notices whose audience is `unspecified`.

A notice with an `unspecified` audience never appears under `student`, `faculty`, or `staff`.

### 5.2 Category values

```json
[
  {"id": "academic", "label": "Academic"},
  {"id": "examination", "label": "Examination"},
  {"id": "admissions", "label": "Admissions"},
  {"id": "events_workshops", "label": "Events and workshops"},
  {"id": "faculty", "label": "Faculty"},
  {"id": "administration", "label": "Administration"},
  {"id": "general", "label": "General"},
  {"id": "other", "label": "Other"}
]
```

### 5.3 Notice list item

```json
{
  "id": "notice-uuid",
  "title": "Example notice title",
  "reference_number": null,
  "category": "examination",
  "summary": "Short source-faithful summary.",
  "audiences": ["student"],
  "important_dates": [
    {
      "kind": "deadline",
      "label": "Last date to submit",
      "starts_on": "2026-11-20",
      "ends_on": null,
      "starts_time": null,
      "source_page": 1
    }
  ],
  "relationship_status": "current",
  "published_at": "2026-11-12T10:30:00Z"
}
```

`audiences` is always a list of audience role values (strings). Descriptive targeting detail (department, year, wording) is returned in the notice detail as `audience_targets`.

### 5.4 Notice detail

```json
{
  "notice": {
    "id": "notice-uuid",
    "title": "Example notice title",
    "reference_number": null,
    "category": "examination",
    "summary": "A fuller summary.",
    "issuing_authority": null,
    "issue_date": null,
    "audiences": ["student"],
    "audience_targets": [
      {
        "role": "student",
        "department": null,
        "year": null,
        "detail": null
      }
    ],
    "important_dates": [],
    "action_items": [],
    "relationship_status": "current",
    "related_notices": [],
    "field_labels": {
      "title": "ai_extracted",
      "summary": "ai_extracted"
    },
    "source_file": {
      "available": true,
      "download_url": "short-lived-url-or-null"
    },
    "published_at": "2026-11-12T10:30:00Z",
    "updated_at": "2026-11-12T10:30:00Z"
  }
}
```

`field_labels` values are `ai_extracted` or `human_corrected`, derived from `field_sources`.

The backend decides which extracted body text, source excerpts, and provenance are suitable for public display. Never return private storage paths or raw internal records.

### 5.5 Processing and publication states

Processing:
- `pending`
- `processing`
- `completed`
- `failed`

Publication:
- `held`
- `published`
- `withdrawn`

Relationship:
- `current`
- `superseded`
- `amended`
- `extended`
- `cancelled`

These dimensions must not be collapsed into one status value.

### 5.6 Nested shapes

**Important date** (an event or deadline; field names match `notice_dates`):

```json
{
  "kind": "deadline",
  "label": "Last date to submit",
  "starts_on": "2026-11-20",
  "ends_on": null,
  "starts_time": null,
  "source_page": 1
}
```

`kind` is `event` or `deadline`. `ends_on` is used only for a date range. The issue date is not returned as an important date; it is the separate `issue_date` field.

**Action item**:

```json
{
  "description": "Submit the form to the department office.",
  "role": "student",
  "department": null,
  "year": null,
  "due_date": null,
  "source_page": 1
}
```

`role` is an audience value or `null`. `due_date` is present only when the source supports it.

**Related notice** (returned only when the related notice is also publicly visible and the relationship is confirmed):

```json
{
  "notice_id": "notice-uuid",
  "title": "Related notice title",
  "relation": "amends",
  "direction": "earlier"
}
```

`relation` is `amends`, `replaces`, `extends`, or `cancels`. `direction` is `earlier` when the related notice is the earlier notice and this notice is the later one, and `later` when the related notice is the later notice.

## 7. Public API contracts

### 7.1 Health

`GET /api/v1/health`

Response:

```json
{
  "status": "ok"
}
```

Do not expose secrets, internal environment variables, or detailed infrastructure information.

### 7.2 Filter options

`GET /api/v1/filters`

Response:

```json
{
  "audiences": [
    {"id": "student", "label": "Students"},
    {"id": "faculty", "label": "Faculty"},
    {"id": "staff", "label": "Staff"},
    {"id": "all", "label": "Everyone"},
    {"id": "unspecified", "label": "Not specified"}
  ],
  "categories": [
    {"id": "academic", "label": "Academic"},
    {"id": "examination", "label": "Examination"},
    {"id": "admissions", "label": "Admissions"},
    {"id": "events_workshops", "label": "Events and workshops"},
    {"id": "faculty", "label": "Faculty"},
    {"id": "administration", "label": "Administration"},
    {"id": "general", "label": "General"},
    {"id": "other", "label": "Other"}
  ]
}
```

These values must match the database enums and PRD vocabulary. In the audience selector, the value `all` is the unfiltered view (see §5.1). The selector may label that unfiltered option “All”, as the PRD does, while a notice that targets `all` is labelled “Everyone”.

### 7.3 Home briefing

`GET /api/v1/briefing`

Query parameters:
- `audience` (optional): `student`, `faculty`, `staff`, `all`, or `unspecified`, with the meaning given in §5.1.
- `limit` (optional): per-section maximum, subject to backend limits.

Response:

```json
{
  "generated_at": "2026-11-12T10:30:00Z",
  "audience": "student",
  "sections": {
    "this_week": [],
    "coming_up": [],
    "recently_posted": [],
    "action_items": [],
    "recent_changes": []
  }
}
```

`audience` echoes the filter applied (`all` when none was supplied).

The briefing is generated from stored published data. It must not wait for a live Gemini call.

Definitions and item shapes:
- `this_week`: supported events/deadlines in the next seven days. Each item:
  ```json
  {
    "notice_id": "notice-uuid",
    "title": "Example notice title",
    "kind": "deadline",
    "label": "Last date to submit",
    "starts_on": "2026-11-20",
    "ends_on": null,
    "starts_time": null,
    "source_page": 1,
    "relationship_status": "current"
  }
  ```
- `coming_up`: later supported events/deadlines, with the same item shape as `this_week`.
- `recently_posted`: recently published notices, each item a notice list item (§5.3).
- `action_items`: supported actions relevant to the selected audience. Each item:
  ```json
  {
    "notice_id": "notice-uuid",
    "notice_title": "Example notice title",
    "description": "Submit the form to the department office.",
    "due_date": null,
    "source_page": 1
  }
  ```
- `recent_changes`: published notices with confirmed relationships. Each item:
  ```json
  {
    "notice_id": "notice-uuid",
    "title": "Later notice title",
    "relation": "extends",
    "related_notice": {
      "notice_id": "earlier-notice-uuid",
      "title": "Earlier notice title"
    },
    "published_at": "2026-11-12T10:30:00Z"
  }
  ```

In a `recent_changes` item, `related_notice` is `null` when the earlier notice is not publicly visible.

The exact definition of “recently” and the maximum look-ahead period should be configuration values documented before release.

### 7.4 List notices

`GET /api/v1/notices`

Query parameters:
- `audience` (optional; see §5.1)
- `category` (optional)
- `from_date` (optional, `YYYY-MM-DD`)
- `to_date` (optional, `YYYY-MM-DD`)
- `q` (optional keyword)
- `sort` (optional; allowed values must be defined by backend)
- `limit` (optional)
- `offset` (optional)

Response:

```json
{
  "items": [],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 0,
    "has_more": false
  }
}
```

Each item is a notice list item (§5.3). Only published public-safe notices may be returned. Held and withdrawn notices must not leak through list filters.

### 7.5 Notice detail

`GET /api/v1/notices/{notice_id}`

Response: the `notice` object defined in §5.4.

If the notice does not exist or is not publicly visible, return `404` without confirming the existence of a private record.

The download URL, when present, must be short-lived or otherwise controlled. It must not expose a private storage path or long-lived privileged credential.

### 7.6 Keyword search

`GET /api/v1/search`

Query parameters:
- `q` (required): search text.
- `audience` (optional; see §5.1)
- `category` (optional)
- `limit` (optional)
- `offset` (optional)

Response:

```json
{
  "query": "physics practical",
  "items": [
    {
      "notice": {
        "id": "notice-uuid",
        "title": "Example notice title",
        "summary": "Short summary.",
        "relationship_status": "current"
      },
      "matched_text": "Relevant excerpt from the notice.",
      "source_page": 2,
      "match_type": "keyword"
    }
  ],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 1,
    "has_more": false
  }
}
```

Baseline search is keyword/full-text search. Do not return `semantic` or `hybrid` as a match type unless those modes are separately approved and implemented.

### 7.7 Ask a question

`POST /api/v1/ask`

Request:

```json
{
  "question": "When is the last date to submit the form?",
  "audience": "student"
}
```

`audience` is optional and follows §5.1.

Answered response:

```json
{
  "answer": "The last date is 20 November 2026.",
  "status": "answered",
  "citations": [
    {
      "notice_id": "notice-uuid",
      "notice_title": "Example notice title",
      "page": 1,
      "excerpt": "The last date for submission is 20 November 2026."
    }
  ]
}
```

Not-found response:

```json
{
  "answer": "I could not find this information in the available published notices.",
  "status": "not_found",
  "citations": []
}
```

Uncertain response (evidence is contradictory or insufficient to give a reliable answer):

```json
{
  "answer": "The available notices do not give a consistent answer to this question.",
  "status": "uncertain",
  "citations": []
}
```

`status` is one of `answered`, `not_found`, or `uncertain`. An `uncertain` response may include citations to the conflicting passages.

Requirements:
- Use only retrieved passages from published public-safe notices.
- Apply audience filters before retrieval evidence is sent to Gemini.
- Citations must refer to actual retrieved source passages.
- If evidence is missing, contradictory, or insufficient, return `not_found` or `uncertain` rather than guessing.
- Do not use general model knowledge to answer college-notice questions.
- Rate-limit the endpoint and bound input/output size.

### 7.8 Submit error report

`POST /api/v1/notices/{notice_id}/reports`

Request:

```json
{
  "issue_type": "incorrect_information",
  "description": "The displayed deadline appears incorrect."
}
```

`issue_type` must be one of the baseline controlled values:
- `incorrect_information`: Incorrect date, deadline, title, or authority details.
- `broken_link_or_file`: Original notice file unreadable or download link failing.
- `missing_dates_or_details`: Key dates, criteria, or action items missing from extraction.
- `duplicate_notice`: Notice has already been published.
- `other`: Other issue described in `description`.

Additional types may be configured by the backend (see §13).

Response:

```json
{
  "report_id": "report-id",
  "status": "received"
}
```

Requirements:
- The referenced notice must be publicly visible.
- Validate issue type and description length.
- Apply rate limits and abuse protection.
- Do not let a report directly modify or hide a notice.
- The backend creates the report record; anonymous clients do not receive unrestricted database insert access.

## 8. Uploader API contracts

All routes in this section require authentication and uploader authorization.

### 8.1 Upload files

`POST /api/v1/uploader/notices`

Content type: `multipart/form-data`

Fields:
- `files`: one or more allowed files.
- No metadata field is required in the baseline; optional metadata can be added through a reviewed contract change.

Example response:

```json
{
  "accepted": [
    {
      "notice_id": "notice-uuid",
      "filename": "notice.pdf",
      "processing_status": "pending",
      "publication_status": "held"
    }
  ],
  "rejected": [
    {
      "filename": "unsupported.docx",
      "code": "UNSUPPORTED_FILE_TYPE",
      "reason": "This file type is not supported."
    }
  ]
}
```

Requirements:
- Validate file content/type, size, and batch limits on the backend.
- Verify uploader permission.
- Store the original before reporting the file as accepted.
- Create a stable notice ID and processing record for each accepted file.
- One rejected file must not block other valid files in the batch.
- Upload acceptance does not mean publication.
- Do not expose storage paths in the response.

File-size, page-count, allowed formats, and batch limits must be configured and documented before implementation.

### 8.2 Processing status

`GET /api/v1/uploader/notices/{notice_id}/status`

Response:

```json
{
  "notice_id": "notice-uuid",
  "processing_status": "processing",
  "publication_status": "held",
  "stage": "text_extraction",
  "message": "Extracting text from the uploaded document.",
  "updated_at": "2026-11-12T10:30:00Z"
}
```

The uploader can see processing and publication states separately. Public clients cannot access this route.

### 8.3 Review queue

`GET /api/v1/uploader/review-queue`

Query parameters:
- `limit`
- `offset`

Response:

```json
{
  "items": [
    {
      "notice_id": "notice-uuid",
      "title": "Extracted or provisional title",
      "processing_status": "completed",
      "publication_status": "held",
      "hold_reason": "The extracted deadline could not be verified.",
      "updated_at": "2026-11-12T10:30:00Z"
    }
  ],
  "pagination": {
    "limit": 20,
    "offset": 0,
    "total": 1,
    "has_more": false
  }
}
```

The queue lists notices that are held, need attention, or failed processing. Open public error reports are listed through `GET /api/v1/uploader/reports` (§8.11), and the uploader interface presents both together in the review area. Only authorized uploaders may access the queue.

### 8.4 Review detail

`GET /api/v1/uploader/notices/{notice_id}`

Response:

```json
{
  "notice": {
    "id": "notice-uuid",
    "title": "Extracted title",
    "summary": "Extracted summary.",
    "category": "examination",
    "audiences": ["student"],
    "important_dates": [],
    "action_items": [],
    "processing_status": "completed",
    "publication_status": "held",
    "relationship_status": "current"
  },
  "validation": {
    "issues": [
      {
        "field": "important_dates",
        "message": "Please verify the extracted deadline.",
        "source_page": 1
      }
    ]
  },
  "source": {
    "filename": "notice.pdf",
    "page_count": 2,
    "preview_url": "short-lived-url-or-null"
  },
  "relations": [
    {
      "relation_id": "relation-id",
      "relation": "amends",

      "later_notice_id": "notice-uuid",

  "processing_history": []

```

This route may expose internal review evidence to authorized uploaders, but must not expose provider secrets. `relations` lists detected relationships, confirmed or not, so a reviewer can act on them through §8.12.

### 8.5 Correct fields

`PATCH /api/v1/uploader/notices/{notice_id}`

Request example:

```json
{
  "title": "Corrected notice title",
  "important_dates": [
    {
      "kind": "deadline",
      "label": "Last date to submit",
      "starts_on": "2026-11-20",
      "ends_on": null,
      "starts_time": null,
      "source_page": 1,
      "source_quote": "Last date for submission is 20 November 2026."
    }
  ],
  "correction_note": "Verified against the original PDF."
}
```

Requirements:
- Accept only explicitly editable fields: `title`, `category`, `summary`, `reference_number`, `issuing_authority`, `issue_date`, `audiences`, `audience_targets`, `important_dates`, `action_items`, and `correction_note`.
- Validate field values and source evidence.
- Record old/new values, editor, timestamp, and optional correction note.
- Mark corrected fields as human-corrected.
- Preserve the original file.
- Re-run relevant validation after correction.
- Editing does not automatically publish a held notice.

Exact Pydantic models and editable field set must match the final schema and implementation.

### 8.6 Publish after review

`POST /api/v1/uploader/notices/{notice_id}/publish`

Request:

```json
{
  "confirmation": true
}
```

Response:

```json
{
  "notice_id": "notice-uuid",
  "publication_status": "published",
  "published_at": "2026-11-12T10:30:00Z"
}
```

This route is for a held notice that has been reviewed. The backend must:
- verify authorization;
- require explicit confirmation;
- re-run all blocking validation checks;
- reject publication if blocking issues remain;
- record the actor and publication event.

Notices that pass automatic publication checks may be published by the processing workflow without a manual request.

### 8.7 Retry processing

`POST /api/v1/uploader/notices/{notice_id}/retry`

Request:

```json
{
  "confirmation": true
}
```

Response:

```json
{
  "notice_id": "notice-uuid",
  "processing_status": "pending"
}
```

Requirements:
- Only retry eligible failed/held records according to backend rules.
- Preserve previous processing runs and events.
- Avoid duplicate public notices or destructive replacement.
- Apply bounded retry behavior.

### 8.8 Withdraw notice

`POST /api/v1/uploader/notices/{notice_id}/withdraw`

Request:

```json
{
  "reason": "The source notice has been withdrawn."
}
```

Response:

```json
{
  "notice_id": "notice-uuid",
  "publication_status": "withdrawn",
  "withdrawn_at": "2026-11-12T10:30:00Z"
}
```

The backend records the acting uploader and the reason. After withdrawal, the notice must no longer appear in public briefing, list, search, detail, or Ask retrieval. Preserve its audit and relationship history.

### 8.12 Confirm or reject a detected relationship

`PATCH /api/v1/uploader/relations/{relation_id}`

Request:

```json
{
  "action": "confirm"
}
```

`action` is `confirm` or `reject`.

Response:

```json
{
  "relation_id": "relation-id",
  "outcome": "confirmed"
}
```

`outcome` is `confirmed` or `rejected`.

Requirements:
- Verify authorization.
- Confirming sets the relationship as confirmed, records the confirming user, and updates the earlier notice's `relationship_status` through the backend's validated transition rules (`amends` → `amended`, `replaces` → `superseded`, `extends` → `extended`, `cancels` → `cancelled`; see `DATABASE_SCHEMA.md` §5.7).
- Rejecting removes the unconfirmed relationship and records the action in the notice's processing history.
- A relationship that is not confirmed is never shown publicly and never changes another notice's status.
- Confirming a relationship does not by itself publish a held notice; publication uses §8.6.

## 9. HTTP status codes

| Code | Meaning | Typical use |
|---|---|---|
| `200` | OK | Successful read or update |
| `201` | Created | Report or resource created |
| `202` | Accepted | Upload accepted for background processing |
| `400` | Bad Request | Malformed request |
| `401` | Unauthorized | Missing or invalid authentication |
| `403` | Forbidden | Authenticated user lacks permission |
| `404` | Not Found | Resource absent or not publicly visible |
| `409` | Conflict | Invalid workflow transition or duplicate/conflicting action |
| `413` | Payload Too Large | File exceeds configured size |
| `415` | Unsupported Media Type | Unsupported file type |
| `422` | Unprocessable Entity | Field validation failed |
| `429` | Too Many Requests | Rate limit exceeded |
| `500` | Internal Server Error | Unexpected internal failure |
| `502` / `503` | Upstream/service unavailable | AI, storage, or database dependency unavailable |

Do not expose internal exception details to clients.

Before changing a shared route or response:
1. Describe the issue and proposed change in a GitHub issue or pull request.
2. Identify affected owners/modules.
3. Check consistency with `PRD.md`, `SYSTEM_ARCHITECTURE.md`, and `DATABASE_SCHEMA.md`.
4. Agree on the new request/response shape.
5. Update this document and mock fixtures.
6. Update backend and frontend consumers together or provide a compatible transition.
7. Add or update tests.

Avoid breaking changes during active integration.
